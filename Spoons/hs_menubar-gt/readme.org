* hs_menubar-gt

Reach the icons on the right of the macOS menu bar from the keyboard: the VPN, the
clipboard manager, Bluetooth, the input source. Press one to open its menu, or go straight
to an entry inside it without any menu appearing.

This is a port of the Hammerspoon 1 =hs_menubar= Spoon, which offered a chooser of the
icons themselves. Reaching the entries inside them is new.

* Simple usage

#+begin_src js   :exports both
const mb = hs.loadSpoon("hs_menubar-gt")

mb.choose()                    // choose an icon and open it
mb.choose(true)                // also offer every entry inside every menu
mb.extras()                    // what is in the menu bar now
mb.entries()                   // every entry inside those menus
mb.press("mb-nordvpn")         // open one by name
mb.list()                      // the icons and their names, as lines
mb.menu()                      // the same list as hs_menu-gt buttons
#+end_src

No keys are bound by default.

* Names

Every icon has a name, so it can be selected by typing rather than by locating it on
screen.

| Form                            | When                                          |
|---------------------------------+-----------------------------------------------|
| =mb-<application>=              | the application has one icon                  |
| =mb-<application>-<n>=          | it has several; =n= counts from 1, left to right |
| =mb-<application>-<title>=      | as well, when the icon's own title is usable  |
| =mb-<application>-<entry>=      | an entry inside that icon's menu              |

So =mb-nordvpn= is NordVPN's icon, =mb-nordvpn-disconnect-dmgvpn= is an entry in its menu,
and =mb-control-center-bluetooth= is Bluetooth.

The application's name is used rather than the icon's title because most titles cannot be
typed, or change while the application runs. Measured on one machine: four applications reported an empty title,
one reported none at all, three were a single emoji, and one was =↓37.8MB ↑17.1MB=, which
changes every time its application polls the network. An icon's title is offered as a second name only when
it consists of letters alone, which excludes both cases above.

These names belong to this Spoon. They are deliberately *not* defined as =hs_interactive-gt=
commands: doing so would mean scanning every process at load to find out what to define, and
a command defined from that scan would name an application that may since have quit.

* Opening an icon, and invoking an entry

Opening an icon has the same effect as clicking it: its menu appears, and an entry is then
selected with the mouse or the arrow keys.

Invoking an entry is different. The entry's action runs and no menu appears, so
=mb-deepl-capture-text-on-screen= starts the screen capture directly instead of opening
DeepL's menu for you to choose it.

** Menus that cannot be read in advance

Some applications build their menu only when it is opened. Control Center, NordVPN, Dropbox
and Caffeine are among them. Their entries cannot be listed, so those icons are offered on
their own and opening them is all that is possible — which works while the icon is on
screen, and does not when it is not.

Hammerspoon's own icons used to be in this group and no longer are: their menus are taken
from what their Spoon registered rather than read from the screen. See below.

** Two lists, because reading every menu is slow

| Call            | Offers                       | Cost on one machine |
|-----------------+------------------------------+---------------------|
| =choose()=      | the icons                    | about 100 ms        |
| =choose(true)=  | the icons and their entries  | about 3 s           |

Reading one menu is inexpensive; reading every menu of every icon is not. The deep list is
therefore a separate call and a separate command.

* Why nothing is clicked

An icon is pressed through accessibility, which takes the element and not a position. This
matters more than it sounds.

The menu bar holds more than the notch leaves room for. Measured here, on a 1800pt-wide
display whose notch occupies x=790 to x=1010, leaving a 790pt strip on the right that
sixteen icons already fill:

| Where the icon was                           | Icons |
|----------------------------------------------+-------|
| On the right strip, visible                  |    16 |
| Parked off screen by a menu bar manager      |     6 |
| Under the notch                              |     2 |
| Left of the notch, behind the window title   |     4 |
| Crossing the notch and back as neighbours change |     2 |

Thirteen of thirty had no pixel to click. Sampled every five seconds for two minutes,
seventeen of the thirty moved 55pt each time Control Center's microphone indicator appeared
or went away — further than most icons are wide, so a click aimed where an icon used to be
lands on its neighbour and opens the wrong menu.

Accessibility has none of these problems. An icon parked at x=-4668 presses exactly as well
as one in plain sight.

An icon is still found again by name at the moment it is pressed, rather than kept from the
scan that listed it, because an application can replace its icon at any time and the element
from the earlier scan is then dead.

* Hammerspoon's own icons

These cannot be pressed through accessibility. =performAction("AXPress")= on an element
belonging to the same process delivers the call to the main thread, which is the thread
already executing the JavaScript that made it. Opening a menu then enters a nested modal run
loop, which does not return. Hotkeys and timers stop being serviced and the application has
to be killed.

Clicking was the way around that, and it fails for exactly the reasons above — four of
Hammerspoon's own five icons were parked off screen, where a click cannot land. Worse than
not landing: macOS clamps the pointer to the nearest screen, so a click meant for an icon at
x=-4562 arrived in the top left corner and opened the Apple menu.

So they are not reached through the screen at all. =hs.menubar= is wrapped, and whatever each
Spoon passes to =setMenu= and =setClickCallback= is kept. Choosing one of these calls the
function that Spoon supplied, directly: no menu opens, nothing is pressed, and where the icon
sits never comes into it.

This also reaches menus accessibility cannot read. An icon given a function rather than an
array builds its menu only when opened, so it has no =AXMenu= until then and reads as empty.
The function is held and simply called.

An icon given a click callback instead of a menu — the clipboard's and one other — does its
whole job in that callback, so choosing it calls the callback and nothing has to be on
screen.

** Choosing one of these icons

Its menu is never opened, because opening a menu is the one thing that cannot be done: only a
click could, and a click is what this Spoon is avoiding. Choosing one offers the entries
inside it instead, which is the same set of actions the menu would have shown.

They are offered whether or not the icon happens to be on screen. Clicking it while it is
visible would work, but then what choosing it did would depend on where the notch had pushed
it that minute, which is the thing this Spoon exists to stop mattering.

** The app's own icon

Hammerspoon 2 puts one icon in the menu bar itself — Reload Config, Settings, Open Console,
Quit. It is made in Swift rather than by a Spoon, so there is no registered function to call
and it is read through accessibility like anyone else's.

Pressing an entry is safe even in this process: an entry performs its action and opens
nothing, so no modal run loop is entered. It is opening a menu that deadlocks, and that never
happens here.

** Load this Spoon first

=start()= installs the wrapping, and it has to be in place before any other Spoon creates an
item. A Spoon loaded earlier registers its menu unrecorded, and its icon then falls back to
being read through accessibility — which cannot see a menu built only on opening, and cannot
reach an icon that is not on screen.

In this configuration =hs_menubar-gt= is therefore the first =use()= in =init.js=.

An icon whose menu is a plain array, such as Hammerspoon's own built-in one, is read through
accessibility either way and does not depend on this.

* What counts as an icon

An item is offered when it is enabled and has a size. Advertising =AXPress= is not enough:
Control Center keeps an element for every module it could show — Focus, Screen Mirroring,
Now Playing — whether or not that module is in the menu bar, and the ones that are not come
back disabled, sized 0x0, parked off screen, still listing =AXPress=. Seventeen of its
twenty-four items were these, and pressing one does nothing at all.

* Functions

** extras()

Every icon in the menu bar, in menu bar order per application. Each is
=({application, bundleID, label, index, ofApplication, element, name, alias, own})=.

Nothing is cached and no watcher is installed, so the result describes the menu bar at the
moment of the call.

** entries()

Every entry inside every readable menu, as
=({application, bundleID, item, element, fn, path, name, own})=. =path= names the entry and any
submenus above it, outermost first.

One of the two carries the action. An entry read through accessibility has an =element= and a
null =fn=; one of Hammerspoon's own, taken from the registry, has an =fn= and a null
=element=.

** instrument()

Wrap =hs.menubar= so that what each Spoon gives its items is recorded. Called by =start()=,
and safe to call twice. See "Load this Spoon first".

** choose([deep], [secondary])

Show a chooser and act on what is chosen. With =deep= true, menu entries are offered as
well as the icons. With =secondary= true, what is chosen is right-clicked rather than opened,
and only the icons are offered; =secondaryChoose()= is the name to call for that.

** secondaryChoose()

The same chooser as =choose()=, right-clicking what is chosen instead of opening it. Only the
icons are offered: an entry inside a menu has one action and no second one.

** peek(), peekHide(), peekToggle()

Draw the icons that cannot be seen in a strip below the menu bar, aligned right, for
=peekSeconds= seconds. Clicking one does what choosing it from the chooser does.
Right-clicking one asks for its secondary menu; because the click itself cannot reach an icon
the strip draws, what happens instead is that the entries inside it are offered in the
chooser. See =secondaryPress()=.

Each is drawn as its own title where it has one. Most of the hidden ones do have a title — a
countdown, a bandwidth reading, an emoji — and for those the strip shows exactly what the menu
bar would have.

An icon with no title cannot be reproduced: there is no way to read the glyph an application
draws into its own menu bar item. =HSImage= builds from a path, a name, an SF Symbol, an
application bundle or a URL, and none of those is the item; =hs.window.snapshotForID()= could
photograph the item's window, but nothing exposes the window ids of the menu bar. So the
application's own icon stands in — and where the application has no icon either, its name
does.

*** Applications with no icon

=HSImage.fromAppBundle()= cannot be asked whether an application has an icon. It resolves the
bundle id, and if that succeeds it returns NSWorkspace's icon for the bundle, which for a
bundle declaring no icon is the generic grey placeholder rather than nothing. Its fallback
symbol does not apply either: that is only for a bundle id which cannot be resolved at all.

Two applications here are in exactly that position. Fleet Desktop lives outside /Applications,
at =/opt/orbit/bin/desktop/macos/stable=, and has no =Resources= directory at all;
SystemUIServer is a faceless system agent. Both came back as the same grey placeholder, which
says nothing about which item it is and is worse than no icon at all, because it looks like
one.

So the bundle's =Info.plist= is read, through =hs.plist=, and its icon used only when it
declares =CFBundleIconFile= or =CFBundleIconName=. Otherwise a name is drawn instead, while
Dropbox and Caffeine keep their icons. The answer is cached per bundle path, a bundle not
growing an icon while it runs.

*** Where the name comes from

The application's name is not always the useful answer either. SystemUIServer hosts several of
the system's menu extras at once, so naming one after the process that owns it makes Time
Machine and the VPN both "SystemUIServer". The VPN says what it is in =AXDescription=; Time
Machine reports no title, description, value or help at all.

Its menu does say. A macOS menu extra almost always carries an entry naming itself, so that
entry is read:

| Entry in the menu              | Drawn as       |
|--------------------------------+----------------|
| =Open Time Machine Settings…=  | =Time Machine= |
| =Wi-Fi Settings…=              | =Wi-Fi=        |
| =Bluetooth Settings…=          | =Bluetooth=    |

Only the top level of the menu is read, which is one cheap menu rather than the whole tree,
and only for an item that has nothing better to offer. Where even that yields nothing the
application's name is used, which is how =fleet-desktop= is drawn.

A title is measured rather than given the width the icon has in the menu bar. AirDrop's item
is 18pt wide because what it draws there is an icon, while the word "AirDrop" is three times
that, and laying it out at 18pt clips it to "Air". A title is measured for height too, and
both titles and icons are placed on the strip's centre line by their own size: text is drawn
from the top of the frame it is given, so a full-height frame would sit every title higher
than the icons beside it.

What is clicked is neither the title nor the icon but an invisible target over each, the full
height of the strip and the full width of its slot, so the space around a short title answers
to the pointer as well.

*** Why the strip is translucent rather than the menu bar's colour

Copying the menu bar's colour was the alternative, and it is worse. The menu bar has no one
colour: it is translucent over the desktop picture, and measured across this screen it ran
from =#4F8CBC= on the left to =#89B1D0= further right. Any single colour taken from it is
right in one place and wrong everywhere else, and it goes stale as soon as the wallpaper or
the window underneath changes. Sampling it at all would need a screen capture, which means
asking for Screen Recording.

A translucent background takes on whatever is behind it, continuously and for free. Only the
background carries the alpha; titles and icons are drawn over it at full opacity, so they stay
legible whatever is behind. =peekBackground= is where to change it — the menu bar blurs what
is behind it and a canvas cannot, so over a busy window a higher alpha reads better than a
lower one.

** hidden()

The items that are in the menu bar but cannot be seen there. Two ways to qualify: parked off
every screen, or left of the notch, where the application's own menus are drawn on top.

Hammerspoon 2 does not expose NSScreen's safe area, so the notch is worked out rather than
read. A menu bar taller than an ordinary one means there is one, and it is centred and about
an eighth of the width — measured here, 220pt of 1800. =notchFraction= is set a little wider
than that on purpose: guessing wide puts an icon in the strip that could have been seen
anyway, while guessing narrow leaves one out of the strip that cannot be seen at all.

** press(name)

Open an icon, or invoke an entry, by name.

The scan happens after =pressDelay=, immediately before the press, rather than when =press()=
is called. What is pressed is therefore what is in the menu bar at that moment: the icons
move about, and one found a fifth of a second earlier may since have slid under its
neighbour. =press()= returns as soon as the press is scheduled, so =true= means scheduled
rather than done; a name that no longer matches anything reports so in an alert.

** secondaryPress(name)

Right-click an icon by name, so that it shows whatever it shows for a secondary click. Same
scheduling as =press()=: it returns once the click is scheduled, and the icon is found again
at that moment.

An icon that is where it is drawn gets a real right click. Every other icon — which is every
icon the strip shows — has the entries inside it offered in the chooser instead.

*** Right-clicking an icon

Some icons answer a right click with a second, different menu. Caffeine is one.

Accessibility cannot carry a right click. All 23 icons in this menu bar advertise =AXPress=
and nothing else bar the occasional =AXCancel=, and =AXPress= has no button number and no
modifier flags. So the only way to deliver one is to post a click, which is the one thing the
rest of this Spoon avoids — see "Why nothing is clicked" — and it only works when the icon is
what is drawn at its own position.

For an icon the strip shows, it is not. An icon left of the notch is drawn beneath the
frontmost application's own menus, and =hs.ax.elementAtPoint= hit-tests its centre to that
application's =AXMenuBar=. Measured here, with the seven icons the strip was showing:

| Icon                             | Its frame      | What is drawn there      |
|----------------------------------+----------------+--------------------------|
| =mb-caffeine=                    | 948,7.5 32x24  | =AXMenuBar= 0,0 1800x39  |
| =mb-karabiner-console-user-server= | 911,7.5 31x24 | =AXMenuBar= 0,0 1800x39  |
| =mb-systemuiserver-2=            | 995,8.5 22x22  | =AXMenuBar= 0,0 1800x39  |

All seven, including the four of Hammerspoon's own. A click posted at any of those positions
goes to the menu bar. So =secondaryPress()= asks the hit test first, and posts a click only
when the answer is the icon itself.

The click is the only thing that cannot be delivered, though. The menu is readable. Caffeine's
icon has one =AXMenu= child, and following its submenu gives twelve entries, each pressable:

: About Caffeine, Preferences..., Activate for > Indefinitely, Activate for > Short (testing),
: Activate for > 5 minutes ... Activate for > 5 hours, Quit

=AXPress= on one of those does not care where the icon is drawn. So where the click cannot be
posted, =chooseWithin()= offers these and presses the chosen one — the same thing this Spoon
already does for Hammerspoon's own icons, and for the same reason. Hammerspoon's own go
straight there: =hs.menubar= calls a click callback with no arguments, so a Spoon's icon has
no secondary click to tell apart from an ordinary one.

What this does *not* do is tell the two menus apart. An icon exposes one =AXMenu= to
accessibility and there is no way to ask which of its menus that is, so what the chooser
offers is the entries of the menu the icon exposes — for Caffeine that is the right-click menu,
but that is an observation about Caffeine, not a rule.

Posting a click to an icon wherever it is would need an event addressed to an application
rather than to a point on the screen. Hammerspoon 1 had that — =hs.eventtap.event:post(app)=
used =CGEventPostToPSN= — and Hammerspoon 2's =hs.eventtap= posts only to the HID tap.
Drafted as =ai/issue_unfiled_eventtap-post-to-application.md=.

** menu()

The icons as =hs_menu-gt= buttons, each with its application's icon.

** list()

The icons and their names as lines, for reading in the console.

| Setting                | Default | Meaning                                      |
|------------------------+---------+----------------------------------------------|
| =skipApplications=     | =[]=    | applications whose icons are never listed    |
| =namePrefix=           | ="mb-"= | prefix for the generated names               |
| =menuDepth=            | =2=     | levels of submenu to follow when reading     |
| =chooserWidth=         | =0.3=   | chooser width, as a fraction of the screen   |
| =rowsToDisplay=        | =14=    | rows visible at once                         |

| =notchFraction=        | =0.13=  | how much of the width the notch covers       |
| =peekSeconds=          | =4=     | how long the strip stays up; 0 to leave it   |
| =peekHeight=           | =34=    | the strip's height                           |
| =peekOffset=           | =6=     | between the menu bar and the strip           |
| =peekTextSize=         | =14=    | size of the titles in the strip              |
| =peekIconSize=         | =20=    | size of the icons in the strip               |
| =peekGap=              | =12=    | between one icon and the next                |
| =peekMargin=           | =8=     | between the strip and the right of the screen |
| =peekPadding=          | =12=    | between the strip's edge and its contents    |
| =peekBackground=       | black at 0.45 | the strip's colour, as =({red, green, blue, alpha})= |

| =peekForeground=       | white   | the titles' colour                           |
| =logTimings=           | =false= | log how long a scan took                     |

=pressDelay= exists because a menu bar menu closes when another window takes the key window,
and the chooser still holds it when a row is chosen. Pressing without the delay opens the
menu, and the chooser's dismissal then closes it. Raise the delay if a menu still opens and
closes immediately.

Control Center accounts for about eight icons and most of the system ones. To shorten the
list:

#+begin_src js   :exports both
mb.config.skipApplications.push("Control Center")
#+end_src

* Commands

In this configuration, from =init.js=:

| Command                          | Key   | Does                                  |
|----------------------------------+-------+---------------------------------------|
| =menubar-interactive=            | ⇧⌃⌘M  | choose an icon and open it            |
| =menubar-interactive-deep=       | ⇧⌃⌘N  | choose an icon or any entry in a menu |
| =menubar-interactive-secondary=  | —     | choose an icon and right-click it     |
| =menubar-peek=                   | ⇧⌃⌘B  | show the icons that cannot be seen    |

The first three set =runDelay= so they wait for the command chooser to close before opening
their own; see the =hs_interactive-gt= readme for why. =menubar-peek= draws rather than
opening a chooser, so it has nothing to wait for.

=menubar-interactive-secondary= has no key: it is a third command rather than a modifier on
the first because =hs.chooser= cannot tell a secondary selection from an ordinary one — its
=onSelect= is given the chosen row and nothing else, no button and no modifier flags.

* Known rough edges

An item with no title is drawn as its application's icon rather than the glyph it actually
shows, because that glyph cannot be read. Where one application owns several untitled items
they therefore look alike in the strip.

A right click on the strip cannot be delivered as a click. The icons the strip draws are
covered by the frontmost application's menus, and a right click can only be posted to a
position, so the entries inside the icon are offered in the chooser instead. For an icon whose
two menus differ, that is whichever menu the icon exposes to accessibility, which cannot be
asked about. See =secondaryPress()=.
